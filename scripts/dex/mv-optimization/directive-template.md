## Per-candidate execution plan

For each candidate, the executor follows the recipe_chain in order:

1. Try first recipe (`index_only` for all candidates).
2. If first recipe fails the gates → fall through to fallback recipe per harness's degradation rules (see `inventory/mv-optimization.md` §Graceful-degradation rules).
3. If all recipes in the chain fail → record `skipped-no-viable-recipe` with reasons.

The executor MUST NOT improvise outside the recipe chain. If a recipe is missing for a strategy_key, surface as `harness-gap` and stop the candidate.

## Constraints (harness invariants — do not override)

These are restated from the harness for executor convenience. The harness is the source of truth.

1. All `psql` calls wrapped in `doppler run -- bash -c 'psql ...'`.
2. All DDL uses `DEX_DB_URL_DIRECT` (pgbouncer txn-mode incompatible with REFRESH CONCURRENTLY).
3. Migration filenames: timestamp-prefix (`YYYYMMDDHHMMSS_*.sql`).
4. Migrations are idempotent (re-runnable without error).
5. PR opens with `--merge --auto --delete-branch`.
6. Per-candidate cleanup: drop the per-candidate shadow MV (if any) before moving on.
7. `__autoresearch__` schema: assume exists; never depend on `DROP SCHEMA` (PreToolUse hook denies it).

## Out of scope

The executor will NOT:
- Touch any MV outside the candidate set.
- Modify any non-MV relation (tables, views, functions, indexes on tables).
- Modify migration files outside `supabase/migrations/`.
- Open more than 1 PR per candidate.
- Touch row-level data — definition + index changes only.
- Drop the `__autoresearch__` schema.
- Improvise outside the recipe chain (see §Per-candidate execution plan).
