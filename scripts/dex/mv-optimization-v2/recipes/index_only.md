# Recipe: index_only (v2 MCP-native)

The only auto-applicable recipe in v2. No shell, no doppler, no psql. All DB access via `execute_sql` and `apply_migration`.

## When to apply

Validator emits `verdict: ship` for this candidate based on:
1. Anti-pattern catalog hit (patterns 1, 2, or 3 — NOT pattern 4 which is always manual).
2. No existing index already covers the target column(s) (confirmed via `existing_index_check.sql`).
3. MV has `has_unique_idx = true` (required for REFRESH CONCURRENTLY — not strictly required for index addition, but is a proxy for active, maintained MVs).

## Full flow

### Step 1: Capture pre-index EXPLAIN baseline

Run via `execute_sql`:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
<canonical_query_with_realistic_limit>;
```

- Use `LIMIT 50` as the default realistic limit (typical paged UI).
- Record `Execution Time` from the output.
- Confirm the plan shows a Seq Scan or Sort-without-index on the target column.
- If the plan already shows an Index Scan on the target column, STOP — this is a v2 bug; investigate.

**Important — COUNT(*) OVER() interaction:** If the canonical includes `COUNT(*) OVER()`, the window function forces a full scan (all rows counted). The index on the sort column can only help the sort portion. For paged queries with COUNT(*) OVER(), expect the index to help only when the planner can split the work (unlikely with combined SELECT). Report this honestly in the gate result.

### Step 2: Build the index via execute_sql (CONCURRENTLY)

`apply_migration` wraps SQL in a transaction; `CREATE INDEX CONCURRENTLY` is incompatible with transactions. Solution: run the actual DDL via `execute_sql`, then record the migration row via `apply_migration`.

```sql
-- Step 2a: execute_sql (the real DDL, non-blocking)
CREATE INDEX CONCURRENTLY IF NOT EXISTS
  idx_{mv_short}_{col_short}
  ON {schema}.{mv} USING btree ({col});

-- Step 2b: apply_migration (records the migration row — must be IF NOT EXISTS, no CONCURRENTLY)
-- name: timestamp-prefixed per project_migration_filename_convention
-- Migration name format: YYYYMMDDHHMMSS_{mv_short}_{col_short}_idx
CREATE INDEX IF NOT EXISTS
  idx_{mv_short}_{col_short}
  ON {schema}.{mv} USING btree ({col});
```

Wait for step 2a to complete (CONCURRENTLY is synchronous from the caller's perspective via execute_sql — it blocks until done). Then call apply_migration.

### Step 3: EXPLAIN gate (mandatory — replaces advisor gate)

Run via `execute_sql`:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
<same canonical query with same LIMIT>;
```

Gate passes if **both**:
1. Plan contains `Index Scan` or `Bitmap Index Scan` node referencing `idx_{mv_short}_{col_short}` by name.
2. Execution Time dropped by ≥ 30% vs. pre-index baseline from Step 1.

Gate fails if:
- Planner still shows Seq Scan (index not chosen — may be due to COUNT(*) OVER() forcing full scan).
- Improvement < 30%.

**On gate failure:** Do NOT auto-merge the PR. Open it with a status comment: "EXPLAIN gate failed — [actual plan node] + [actual improvement %]. Index exists on prod and may still provide value for non-windowed queries. Human review required before merge."

**On COUNT(*) OVER() partial scenario:** If the plan shows the index IS used (e.g., for the sort portion) but total Execution Time didn't drop ≥ 30% because the window function adds overhead — record as "partial gate: index adopted by planner but improvement below 30% due to COUNT(*) OVER() window scan. PR left open for human review." Do not auto-merge.

### Step 4: Advisor sweep (hygiene, non-blocking)

Call `get_advisors` with `type: performance` after the index. This is informational only — it does not gate the PR. Record the result. New `unused_index` advisors for this index after a quiet period are expected and normal.

### Step 5: Open PR

Branch: `autoresearch/{mv_short}-{col}-idx-{YYYY-MM-DD}`

PR title: `perf({mv}): add btree on {col} (ORDER-BY-LIMIT-no-idx pattern)`

PR body must include:
- Which anti-pattern catalog entry this targets (name + excerpt from `lib/anti_pattern_catalog.md`)
- EXPLAIN before: plan snippet + Execution Time
- EXPLAIN after: plan snippet + Execution Time
- Improvement % (or explanation of why gate did not clear)
- Migration filename

### Step 6: Auto-merge decision

- Gate passed (≥ 30% improvement + Index Scan node visible): `gh pr merge --merge --auto --delete-branch`
- Gate failed or partial: leave open with status comment. Do not auto-merge.

## Migration template

```sql
-- supabase/migrations/{YYYYMMDDHHMMSS}_{mv_short}_{col_short}_idx.sql
-- Auto-generated by scripts/mv-optimization-v2/recipes/index_only.md
-- Pattern: ORDER-BY-LIMIT-no-idx (anti_pattern_catalog.md entry 3)
-- Baseline: {pre_explain_time_ms}ms → {post_explain_time_ms}ms ({improvement_pct}%)

CREATE INDEX IF NOT EXISTS idx_{mv_short}_{col_short}
  ON {schema}.{mv} USING btree ({col});
```

## Naming convention

- Index name: `idx_mv_{mv_without_mv_prefix}_{col}` — truncated to ≤ 63 chars (PG identifier limit).
- Migration name (passed to `apply_migration` as `name`): `{YYYYMMDDHHMMSS}_{mv_short}_{col_short}_idx` (no `.sql` suffix — `apply_migration` appends it).
- Branch name: `autoresearch/{mv_short}-{col}-idx-{YYYY-MM-DD}`.

## Rollback

```sql
DROP INDEX CONCURRENTLY IF EXISTS {schema}.idx_{mv_short}_{col_short};
```

Forward-only migration convention. Rollback is manual but trivial.
